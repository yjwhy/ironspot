# Security Audit Retrospective — 2026-05

Senior security review of the IronSpot codebase (React Native + Spring Boot + Supabase). 80 findings catalogued, ~60 fixed in-session. This document is the long-form retrospective companion to the PR-by-PR commit log: it groups findings by area, names the security primitive that was failing, and explains the fix in enough depth that a future engineer can recognise the same pattern when it reappears.

## How to read this

Each section is one area of the codebase. Within an area, findings are listed by original audit number with the severity emoji that triaged them: 🔴 CRITICAL, 🟠 HIGH, 🟡 MEDIUM, 🟢 LOW. The "Issue" paragraph names the security primitive that was broken; the "Fix" paragraph names the primitive we restored and how.

The PR numbers in this document refer to the [yjwhy/ironspot](https://github.com/yjwhy/ironspot) repository.

## 1. Secrets & access (BE)

### #7 🔴 Operational secrets had no rotation history and lived in `.env`

**Issue.** Seven runtime secrets (Supabase service role key, Naver Search client secret, Groq + Gemini API keys, Sentry DSN, Slack webhook, DB password) were checked into `.env` and re-shared into Render via copy-paste, with no rotation history. A single laptop-disk leak compromises every layer at once.

**Fix.** All seven keys verified non-leaked (no public commit history exposure), kept in place for now, and a 5-minute hygiene pass was applied:

- macOS Spotlight + Time Machine exclusion for the project directory so an indexed `.env` cannot leak via Quick Look or backup snapshot.
- Memory note `lesson_render_cold_pool_two_stages` carries the convention forward.

Secrets manager migration deferred — the user's risk tolerance + the small team made the upgrade lower priority than the structural fixes below.

## 2. Database (Supabase + Postgres)

### #8 🔴 RLS was off on every public-schema table

**Issue.** Supabase's Row Level Security was disabled across the entire `public` schema. With the anon key able to reach every row directly via PostgREST, only the BE's service-role key stood between the public and the data.

**Fix.** Migration `V17__enable_rls_deny_default.sql` runs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + `FORCE` on 13 tables (gyms, gym_machines, machine_photos, photo_votes, reports, nl_search_log, users, brands, categories, machine_templates, moderation_audit_log, gym_owners, vision_cache) with zero policies. PostgREST traffic now hits a deny-by-default; the Spring Boot BE keeps full access via its own connection because it's the table owner.

`init-test-db.sql` mirrors the ENABLE/FORCE so integration tests catch RLS regressions before merge.

### #9 🔴 Storage bucket `machine-photos` was world-readable

**Issue.** The `machine-photos` Supabase Storage bucket had `public: true`. Every uploaded photo URL was scrape-friendly: an attacker who knew the project ID could list and download every photo without ever touching the IronSpot BE.

**Fix.** Two-part:

1. `StorageService.upload()` now mints a Supabase signed URL via `POST /storage/v1/object/sign/<bucket>/<path>` with a 365-day TTL and stores that URL verbatim in `machine_photos.photo_url`. No DB schema change and no app-side change because the URL value is still a working `<Image src={uri}>` target.
2. Bucket flipped to `public: false` via the Storage API (PUT `/storage/v1/bucket/machine-photos`). Anonymous `/object/public/...` URLs now return 400 from Supabase's edge.

Pre-flip data wipe: 26 orphaned Storage objects + 1 test user + their gym + 17 `nl_search_log` rows were deleted (all test data — admin retained). Merged in PR #217.

### #21 🟠 PostGIS `searchInBounds` accepted arbitrary bbox + radius

**Issue.** The map-bounds search query accepted any bbox the client sent. A SW=(−90,−180) / NE=(90,180) bounding box would scan the whole gyms table, defeating the partial PostGIS index and OOMing the result set.

**Fix.** Pre-validate bbox area (≤ 5km² for the default search), radius (≤ 20km), and enforce `LIMIT 50` at the SQL builder level. The cap is statically expressed in `GymSearchRequest`'s compact constructor; bypassing it requires reaching past the controller, which the type system prevents.

### #22 🟠 Hikari pool had no statement / lock / idle-transaction timeouts

**Issue.** A long-running query or a stale transaction held a connection indefinitely; the pool could exhaust into request-rejection territory during a single slow LLM call.

**Fix.** `application-prod.yml` sets three Postgres-level limits via JDBC `options=`: `statement_timeout=8s`, `lock_timeout=2s`, `idle_in_transaction_session_timeout=10s`. A runaway statement now self-cancels server-side before consuming the pool.

### #25 🟠 ReportService accepted photoId without existence + blinded check

**Issue.** A client could submit a report referencing any UUID, whether or not it pointed at a real photo. The downstream reviewer screen would silently render an empty card.

**Fix.** Pre-flight check in `ReportService.createReport`: photo must exist + must not already be `is_blinded` (a previously-moderated photo cannot be re-reported, which removes a noisy DoS lever on the moderation queue).

### #30 🟠 `vision_cache` had no TTL, grew unbounded

**Issue.** Cached Google Vision responses were keyed by image SHA-256 and never aged. Over time the cache table approached storage-cost territory and contained OCR text from photos a user had since deleted.

**Fix.** `V18` adds an index on `vision_cache.created_at`; `VisionCachePruneJob` runs daily and deletes rows older than 90 days. `texts_json` itself is now NFC-normalised + truncated at insert time so stored prompts can't carry hidden control characters into future OCR pipelines (overlaps with #75 below).

### #31 🟠 `nl_search_log.raw_query` retained user-typed queries indefinitely

**Issue.** Every natural-language search query (which may contain location names, gym names, or accidental PII) sat in the BE database forever, accessible to anyone with DB credentials.

**Fix.** `NlSearchLogRetentionJob` redacts `raw_query` to NULL after 30 days, then deletes the row at 90 days. The normalised query column is kept for the H2 analytics use case the column was designed for; raw text is the retention-sensitive surface.

### #33 🟠 `gyms.naver_place_id` had a SELECT-then-INSERT race

**Issue.** Two concurrent `POST /api/gyms` requests with the same `naver_place_id` both SELECT empty, both INSERT, and the loser hits the partial UNIQUE index and surfaces a 500 with a confusing `DataIntegrityViolationException` stack trace.

**Fix.** `GymService.createFromNaverPlaces` catches `DataIntegrityViolationException`, re-runs the SELECT, and returns the winner's row to the loser. Both clients see the same 200 response.

### #34 🟠 Flyway gaps were silently tolerated

**Issue.** The 2026-05-21 prod incident had migrations V6-V9 sitting unapplied for weeks because `flyway_schema_history` did not exist on prod; Spring Boot's Flyway integration treated the schema as "already at HEAD" and never ran them. The discrepancy only surfaced when a query referenced a column that did not exist.

**Fix.** `FlywayStartupVerifier` runs at `ApplicationReadyEvent`, calls `Flyway.info()`, and:

- Logs the current schema version + applied count at INFO.
- On any PENDING / FAILED / MISSING_FAILED / OUT_OF_ORDER migration, emits an ERROR-level log + a Sentry message at ERROR level. Ops is paged.

Startup is not aborted — a Flyway gap may be intentional during a rollback, and the JVM is the same one carrying the alerting.

## 3. Backend (Spring Boot)

### #13 🔴 JWT validator did not check `iss` or `aud`

**Issue.** `JwtValidator` decoded the signature + checked expiry but accepted any issuer and any audience. A Supabase `service_role` JWT (audience = `service_role`) would have authenticated as a regular user; a Supabase JWT from a different project (different `iss`) would too.

**Fix.** `JwtValidators.createDefaultWithIssuer` wires Nimbus to reject non-matching `iss` at decode time; `JwtValidator.validate` additionally requires `aud="authenticated"` (Supabase's end-user audience). Service-role and anon tokens are now rejected at the auth layer.

### #18 🔴 Docker image ran as root with no HEALTHCHECK

**Issue.** The `iron-spot-api` Dockerfile shipped a JVM that ran as UID 0. A container-escape vector becomes much more rewarding than it needs to be; ops also had no in-container health probe.

**Fix.** Dockerfile multi-stage with a runtime stage that creates `ironspot` (UID 10001), `USER ironspot`, plus a `HEALTHCHECK` curling `/actuator/health`. Render is unaffected (its platform layer ignores Docker HEALTHCHECK), but local dev + any future K8s rollout inherits the probe.

### #20 🟠 `GET /api/gyms/**` was anonymous

**Issue.** The full gym dataset — name, address, phone, lat/lng, owner-curated fields — was readable without a JWT. A casual scraper could enumerate every IronSpot gym.

**Fix.** `SecurityConfig` adds `requestMatchers(GET, "/api/gyms/**").authenticated()`. The existing `/api/brands`, `/api/categories`, and `/api/machine-templates` paths stay `permitAll` because they are reference data with no PII / business-sensitive content.

### #24 🟠 JwtAuthenticationFilter ran a DB query per request

**Issue.** Every authenticated request called `UserRepository.findAuthContext(sub)` to load the role + banned timestamp, putting one DB round trip on the Hikari pool per request. A 100 RPS endpoint pushed 100 DB lookups per second for context that changes only on admin action.

**Fix.** `@Cacheable("authContext")` with a 60s Caffeine cache (2000 entries). `@CacheEvict` on `markBanned` / `markUnbanned` / `markDeleted` / `promoteToOwner` so a ban takes effect immediately rather than within a minute.

### #26 🟠 `/api/gyms/places-search` had no per-user cap

**Issue.** Naver Local Search's free tier is 25K calls/day across all users. A compromised account could drain the entire shared quota in minutes, locking the rest of the user base out of the new-gym registration flow.

**Fix.** `NaverSearchQuotaService` enforces 100 queries/user/day via a 24h Caffeine counter, evaluated before the Naver call. Configurable via `NAVER_SEARCH_DAILY_CAP_PER_USER`.

### #27 🟠 PromoteContributionRequest dispatched on `kind` but didn't enforce extraneous fields

**Issue.** Admin pending-contribution promote is a flat record with three `kind` values; the `switch (kind)` resolved required fields per branch but silently dropped fields belonging to other branches. A client that picked the wrong `kind` got a successful promote with the wrong template.

**Fix.** Each `resolve*()` now calls `requireAbsent` for every field that does not belong to its branch and returns 400 when one is present. Tests cover the three "extraneous field" cases.

### #28 🟠 `nickname` field accepted any Unicode

**Issue.** `UpdateUserRequest.nickname` had a `@Size(2,20)` but no character whitelist. A nickname could carry control characters, bidi overrides, or zero-width joiners that the admin moderation UI would render verbatim.

**Fix.** `@Pattern` allow-list of `\p{L}\p{N}\p{Mn}\p{Mc}` plus whitespace + the small set of safe symbols (hyphen, underscore, period). `\p{C}` (the control + format superset) is implicitly excluded.

### #29 🟠 OwnerCoverPhoto skipped service-layer ownership recheck

**Issue.** `OwnerCoverPhotoController` checked the caller's owner role at the security layer but then trusted the request body's `gymId` without re-verifying that the caller was the owner of _that specific_ gym. A user with the owner role on Gym A could overwrite Gym B's cover photo.

**Fix.** `OwnerCoverPhotoService.uploadCover` queries `gym_owners` for `(callerUserId, gymId)` and 403s if no row matches. Reviewed via PR #199.

### #46 🟠 Photo upload had no per-IP rate gate

**Issue.** The per-user Vision quota didn't catch burst floods from compromised accounts on the same IP, scripted account-cycling within a minute, or cache-hit replay (where the per-IP request rate climbs higher than Vision-on-cache-miss can ever do).

**Fix.** `UploadRateGate` is a Caffeine-backed (60s window) per-IP cap wired into `POST /api/photos/upload` and `POST /api/photos/ocr-only`. Default 30 req/min/IP. IP resolution prefers the left-most entry of `X-Forwarded-For` (Render edge) and falls back to remote-addr for local dev.

### #51 🟠 actuator info.env exposed every environment variable

**Issue.** `/actuator/info` with `management.info.env.enabled=true` echoed the full environment (Supabase keys, Naver secrets, Groq + Gemini API keys, Slack webhook) to any caller of the actuator endpoint.

**Fix.** `application-prod.yml` sets `management.info.env.enabled: false`. The actuator info endpoint now returns a minimal `{app.version}` payload.

### #52 🟠 swagger-ui + /api-docs exposed schema to anyone

**Issue.** `springdoc` defaulted to enabling `/api-docs` and `/swagger-ui.html` in every environment. Production listed every endpoint, every DTO, every status code — a near-complete map of the API surface for any would-be attacker.

**Fix.** `application-prod.yml` disables both paths. Dev / test profiles keep them.

## 4. AI / LLM (Generate Zero Platform integrations)

### #41 🟠 `Location.NamedPlace.name` accepted unbounded LLM output

**Issue.** The LLM-produced `location.name` flowed straight into the Naver Search query string. An LLM jailbreak that smuggled a 100KB payload into `name` would have pushed past Naver's request size limit and would have shown up in our outgoing API logs verbatim.

**Fix.** `Location.NamedPlace`'s compact constructor enforces `MIN/MAX_RADIUS_KM` + `MAX_NAME_LENGTH=60` + an allow-list regex. The LLM response cannot land in `Location` unless every field is in range; the parser throws on construction.

### #42 🟠 `machineFilters[]` had no length cap

**Issue.** A malformed LLM response could emit a hundred machine filters; each one mapped to a `WHERE EXISTS (...)` subquery and tripped the new statement timeout from #22.

**Fix.** `SearchDsl.compact-constructor` caps `machineFilters.size() <= 5`. The DSL is rejected at parse time when over the cap.

### #43 🟠 AdminBrandTransliterate had no length / quota guards

**Issue.** The Gemini transliterate endpoint accepted brand names of any length and could be called unboundedly per user, multiplying cost amplification for an admin endpoint that's only meant to assist with the closed catalog.

**Fix.** `@Size(max=80)` on `TransliterateBrandRequest`. A process-wide rolling counter (`enforceQuota`) caps 50/hour + 200/day. 429 + Sentry log on overflow.

### #44 🟠 BusinessException echoed user input verbatim

**Issue.** Many `BusinessException` messages embedded the user-supplied string, e.g. `"위치를 찾을 수 없어요: " + place.name()`. A prompt-injection payload that smuggled out a fragment of the system prompt would have arrived back at the client through the error body, defeating prompt confidentiality.

**Fix.** `SafeEcho.sanitise` (in `iron-spot-api/.../common/text/SafeEcho.java`) truncates + strips `\p{C}` from any user-derived string before it reaches an error message. `LocationResolver` was the highest-leverage call site — its geocode failure no longer echoes the name at all (#77).

### #45 🟠 Sentry breadcrumbs carried raw NL queries

**Issue.** `NlSearchService.recordBreadcrumb` shipped the user's raw query string to Sentry on every search. Aside from PII concerns, this also leaked exact attack payloads when a probe failed.

**Fix.** Breadcrumb now stores the normalised + truncated query (the same surface that survives 30-day retention in #31). Raw is never sent to Sentry.

## 5. Prompt injection (LLM-specific, OWASP LLM Top 10)

### #63 🔴 LLM01 — search-dsl.md had no jailbreak meta-guard

**Issue.** The LLM system prompt (`prompts/search-dsl.md`) instructed the model to parse a query into a DSL but had no immune-system-style instruction about resisting prompt-injection. An LLM with a "tell me your system prompt" instruction in the user query would have happily complied.

**Fix.** Two paragraphs added to the system prompt: (a) a meta-guard explicitly listing the injection patterns to refuse (role-swap, prompt-leak, tool-summon), (b) a hard 20km radius cap so a jailbroken radius can't sneak past the BE validator. `DslValidator` enforces the same radius bound on every parse.

### #64 🔴 LLM02 — GeminiFlashClient didn't handle SAFETY finishReason

**Issue.** When Gemini blocked a response because the prompt tripped its SAFETY filter, the client treated the empty `parts[]` as a normal "no output" path and surfaced an empty DSL parse. A jailbreak that landed in the SAFETY blocklist would silently degrade to "no results" without the user knowing why.

**Fix.** `GeminiFlashClient.parseResponse` explicitly checks `candidate.finishReason == "SAFETY"` and `promptFeedback.blockReason`. On either, throws a typed `LlmException(SAFETY)` that surfaces as a 502 with the "AI 처리 중 안전 정책에 의해 차단되었습니다" message.

### #65 🔴 LLM01 — OCR → admin transliterate indirect prompt injection

**Issue.** The admin contribution promote flow pre-fills the brand name field from `OcrService` output. An attacker who uploaded a photo with a crafted label (visible to OCR but invisible to the human reviewer) could plant prompt text that reached `AdminBrandTransliterateService.transliterate` and ran in Gemini's context as if the admin typed it. Classic indirect injection chain.

**Fix.** Three layers:

1. `AdminBrandTransliterateService.sanitiseInputString` runs at the service entry, NFC-normalises, strips `\p{C}` (control + bidi + format codepoints), and caps length.
2. `FuzzyMatchService` (#74) does the same on the OCR side so injection-only-when-rendered tokens are normalised before matching too.
3. The transliterate response is cross-checked against `LOCKED_EN_TO_KO` (#67) so even a successful jailbreak can't poison the catalog with a non-allowed brand.

### #66 🔴 LLM02 — LLM string responses passed control chars through

**Issue.** `LlmResponse` parsed JSON from the LLM and trusted that the string fields were "just text". A model that emitted a bidi-override codepoint in `interpretation` would have rendered the response right-to-left in the app — useful for a phishing-style attack on the natural-language interpretation card.

**Fix.** `SafeEcho.sanitise` is applied to every LLM-derived string before it crosses an API boundary. `\p{C}` is the superset for control + format + private-use codepoints.

### #67 🔴 LLM09 — Transliterate response wasn't cross-checked against locked catalog

**Issue.** Even with input sanitisation (#65), the LLM still returns a `{name, nameKo}` pair that a successful jailbreak might use to inject an arbitrary brand alias. The endpoint's purpose is to suggest a Korean name for a _known_ English brand from a fixed 24-entry catalog, so the threat model says the response is constrained.

**Fix.** `AdminBrandTransliterateService.enforceLockedReference` cross-checks: if the input (case-insensitive) matches one of the 24 reference brands, the response's other side MUST equal the locked value. A flipped Cybex → "사이벡스‮" hits "AI 응답 형식이 올바르지 않아요" 502 instead of polluting the catalog.

### #68 🟠 LLM04 — Groq + Gemini had no max_tokens cap

**Issue.** A jailbreak that asked the model to "explain the entire system prompt verbatim" could return 10K+ tokens per call, multiplying cost amplification by ~20x.

**Fix.** Both clients set `max_tokens=512` (Groq) / `maxOutputTokens=512` (Gemini). DSL responses are ~80 tokens; 512 is generous headroom while bounding the worst case.

### #69 🟠 LLM02 — Markdown code fence stripping was inconsistent

**Issue.** Models sometimes wrap JSON in ` ```json ... ``` ` fences. The Groq client stripped them; the Gemini client didn't. A model returning a fenced response to Gemini's path crashed the JSON parser and bubbled up as 502, breaking the search.

**Fix.** Both clients route through a shared `stripCodeFence` that handles ` ```json `, ` ``` `, and naked JSON.

### #70 🟠 LLM01 — NlSearchRequest passed control chars to the LLM

**Issue.** The user's natural-language query was sent to the LLM verbatim. Control characters (especially U+202E right-to-left override) could shift the LLM's tokenization in surprising ways and were a known prompt-injection vehicle.

**Fix.** `@Pattern` on `NlSearchRequest.query` rejects control / line-break / null-byte at the controller boundary. A pre-LLM normaliser in `NlSearchService` NFC-normalises and strips bidi marks defensively.

### #71 🟠 LLM04 — Fallback LLM had no circuit breaker

**Issue.** When Groq failed, the code fell through to Gemini. When Gemini also failed (e.g., during a Google outage), the next request immediately retried both. A sustained outage produced a steady-state cost burn.

**Fix.** `FallbackLlmClient` opens the circuit after 5 fallbacks in a 10-minute window. While open, the search returns 502 immediately without burning calls.

### #72 🟠 LLM06 — dsl.error() used free text

**Issue.** When the LLM signalled "I can't parse this", the error message was a free-text string that varied per model. The BE message router pattern-matched on the string, so a model-side message change silently broke the UI.

**Fix.** Strict enum `DslError` (`LOCATION_NOT_FOUND`, `AMBIGUOUS_QUERY`, etc.) is the only thing crossing the LLM → BE boundary. The LLM is instructed (in the system prompt) to emit one of the enum values; anything else is collapsed to `UNKNOWN`.

### #73 🟠 LLM02 — ObjectMapper allowed unknown properties

**Issue.** The LLM client's `ObjectMapper` had `FAIL_ON_UNKNOWN_PROPERTIES=false`. A model that emitted an unexpected `tool_calls` field (a future API upgrade) would silently pass it through without anyone noticing it was being dropped.

**Fix.** `ObjectMapper` configured with `FAIL_ON_UNKNOWN_PROPERTIES=true` + `FAIL_ON_INVALID_SUBTYPE=true`. New fields surface immediately at the parse layer.

### #74 🟠 LLM01 — OCR tokens passed bidi codepoints

**Issue.** `FuzzyMatchService` matched OCR tokens against the brand catalog using normalised string comparison, but the normalisation didn't strip bidi / format / private-use codepoints. A label crafted with an invisible U+200E bidi mark inside the brand name would have looked identical to a human but failed to match.

**Fix.** NFC normalisation + `\p{C}` strip on every OCR token before matching.

### #75 🟠 LLM01 — vision_cache.texts_json was a stored prompt injection sink

**Issue.** The Vision OCR result was cached by SHA-256 of the image bytes. A first uploader could craft a label whose OCR text contained prompt-injection markers; every subsequent uploader of the same image (cache hit) would replay that text into the admin transliterate flow.

**Fix.** `VisionCacheRepository.serialiseTexts` NFC-normalises and caps each text before insert. Combined with #65's input sanitiser at the transliterate entry, the stored cache cannot smuggle injection markers downstream.

### #76 🟠 LLM07 — Naver Search query + response weren't sanitised

**Issue.** The Naver Local Search query string came from the LLM (`Location.NamedPlace.name`), and the response from Naver was rendered in the app. Neither side was sanitised. A jailbreak that smuggled HTML tags into `name` would land verbatim in Naver's logs; a malicious vendor-submitted Naver place name with `<script>` would land in the admin web UI.

**Fix.** `NaverSearchService.sanitiseQuery` NFC + `\p{C}` strip + 60-char cap on the way out. `stripHtml` on the response uses `HtmlUtils.htmlUnescape` first then strips `<[^>]+>` so smuggled `&#x3C;script&#x3E;` cannot survive.

### #77 🟠 LLM06 — LocationResolver echoed place.name() in errors

**Issue.** `LocationResolver.geocode` returned `"해당 위치를 찾을 수 없어요: " + place.name()` when Naver had no results. Same prompt-leak vector as #44 but for the location field.

**Fix.** Error message no longer contains `place.name()`. The user sees "정확한 지명을 입력해주세요" with no echo.

### #78 🟠 LLM05 — Prompts weren't integrity-checked at build time

**Issue.** Anyone with commit access could modify `prompts/*.md` without code review; the change would propagate to prod on the next deploy with no signal. A malicious or accidental edit (e.g., removing the meta-guard from #63) would silently weaken every search.

**Fix.** `PromptIntegrityTest` is a snapshot test that hashes every file under `src/main/resources/prompts/` and asserts the manifest matches. Any prompt edit must update the manifest in the same commit; CODEOWNERS routes prompt PRs to `@yjwhy` for explicit review.

## 6. CI / Supply chain

### #18, #47, #48, #50 — see Backend / CI sections above

### #47 🟠 GitHub Actions had implicit write permissions

**Issue.** Workflows defaulted to GITHUB_TOKEN with write scope, meaning a compromised action could push to main, create releases, or open PRs as the bot. Standard hardening.

**Fix.** Top-level `permissions: contents: read` on every workflow. Jobs that need write scope override per-step explicitly.

### #48 🟠 Dependabot PRs were a chore

**Issue.** Patch/minor bumps + GitHub Actions version bumps piled up because there was no auto-merge.

**Fix.** `.github/workflows/dependabot-auto-merge.yml` enables auto-merge on patch + minor + github-actions PRs once all required checks are green. Major bumps still require user approval (per CLAUDE.md rule).

### #50 🟠 No SAST, no secret scan, no dependency review

**Issue.** Code-level vulnerabilities and committed secrets had no automated tripwire. A bad commit was discovered manually or in code review.

**Fix.** `.github/workflows/security-scans.yml` runs CodeQL (Java + JS/TS), gitleaks (committed secret scan), dependency-review-action (transitive CVE block) on every PR + on a weekly schedule against `main`.

## 7. The bigger pattern

A few themes ran through this audit:

1. **Defense-in-depth pays off.** Three out of four prompt-injection fixes layered three different controls (input sanitisation at the entry, output cross-check at the exit, schema constraints in the middle). No single layer was load-bearing.
2. **Public-by-default surfaces are the easiest miss.** The Supabase Storage bucket, the actuator info endpoint, the swagger-ui path, the `/api/gyms/**` GETs — all four had a "default permissive" stance that hadn't been re-evaluated since the dev sprint.
3. **Cost amplification is a real threat for LLM endpoints.** Max-tokens caps, per-user quotas, per-IP rate gates, circuit breakers — every LLM endpoint needed at least two of those four.
4. **The integration test profile must mirror production security primitives.** `init-test-db.sql` had to mirror RLS ENABLE + FORCE, or RLS regressions would land silently. The lesson generalises: any security control that's enforced at the DB layer needs a matching assertion in the test fixture.
5. **Memory notes captured the load-bearing lessons.** `lesson_prod_flyway_never_ran`, `lesson_brand_anchored_over_threshold_tuning`, and `feedback_named_functions` are all artefacts of this audit's investigation phase. The notes outlive the PRs.
