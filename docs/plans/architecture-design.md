# IronSpot Architecture Design

- Version: 2.0
- Date: 2026-04-17
- Author: YJ (builtByYJ)

## 1. Project Overview

**Purpose:** Help users find specific gym machines (Panatta, Hammer Strength, etc.) by providing real equipment availability and verified photos of nearby gyms.

**Core Value:** Eliminate wasted trips, curate "expedition workouts," and keep data fresh through community-driven updates.

**Goals:**

- Portfolio: Full-stack architecture, AI integration, solid engineering fundamentals (frontend/fullstack/backend positions)
- Product: Real App Store launch with scaling path

## 2. Architecture Overview

```
[React Native (Expo)]
        |
   Phase 1: Supabase direct
   Phase 2+: Spring Boot API server
        |
[Supabase (PostgreSQL + PostGIS + Storage + Auth)]
        |
   Phase 2: Google Vision API (OCR)
   Phase 3: LLM API (Natural Language -> Structured Query)
```

### Phase Strategy

| Phase | App -> Data Path                | What's Added                                  |
| ----- | ------------------------------- | --------------------------------------------- |
| 1     | Expo -> Supabase direct         | Map, filters, photo viewing (read-only)       |
| 2     | Expo -> Spring Boot -> Supabase | Auth, photo upload, OCR, machine data updates |
| 3     | Same                            | Natural language text-to-query pipeline       |

**Why this structure:**

- Phase 1 with direct Supabase delivers a working MVP fast -> portfolio-ready at any point
- Phase 2 introduces Spring Boot by swapping data source (data source abstraction)
- Business logic concentrated in Spring Boot -> proves backend design capability in one place

### Phase 1 -> Phase 2 Transition Strategy

Phase 1 calls Supabase directly via `supabase-js`. Phase 2 introduces Spring Boot as the API layer.

**Approach: Data source abstraction layer**

- Phase 1: all data fetching goes through service files (`src/features/*/services/`)
- Services use Supabase client internally
- Phase 2: swap service internals from Supabase client -> ky HTTP calls to Spring Boot API
- Components and hooks stay unchanged -> only service layer changes
- Transition is per-feature (auth first, then photo upload, then search)

```
Phase 1:  useGymSearch hook -> gymSearchService -> supabase.rpc()
Phase 2:  useGymSearch hook -> gymSearchService -> ky.get('/api/gyms/search')
                                                   (auto-generated by Orval)
```

## 6. Database Design

```sql
-- Users
Users
  id          uuid PK (references auth.users)
  email       text NOT NULL
  nickname    text NOT NULL
  role        enum (admin | user | owner)
  created_at  timestamp
  updated_at  timestamp

-- Gyms
Gyms
  id               uuid PK
  name             text NOT NULL
  address          text NOT NULL
  location         geography(Point) -- PostGIS
  phone            text (nullable)
  operating_hours  text (nullable)       -- e.g., "06:00-23:00"
  day_pass_price   integer (nullable)    -- in KRW
  is_verified      boolean
  last_verified_at timestamp
  created_at       timestamp
  updated_at       timestamp

-- Equipment taxonomy
Brands
  id    uuid PK
  name  text UNIQUE  -- e.g., Panatta, Hammer Strength

Categories
  id    uuid PK
  name  text UNIQUE  -- e.g., Back, Chest, Legs

Machine_Templates
  id            uuid PK
  brand_id      FK -> Brands
  category_id   FK -> Categories
  name          text  -- e.g., "High Row"
  loading_type  enum (pin | plate)
  is_approved   boolean  -- admin approval flag
  created_at    timestamp
  UNIQUE(brand_id, name)

-- Gym-specific data
Gym_Machines
  id               uuid PK
  gym_id           FK -> Gyms
  template_id      FK -> Machine_Templates
  quantity         integer DEFAULT 1    -- how many of this machine
  is_custom        boolean
  custom_name      text (nullable)
  last_verified_at timestamp
  created_at       timestamp

Machine_Photos
  id              uuid PK
  gym_machine_id  FK -> Gym_Machines
  user_id         FK -> Users (nullable in Phase 1 seed, required Phase 2+)
  photo_url       text NOT NULL
  created_at      timestamp
  upvote_count    integer DEFAULT 0  -- denormalized for query performance

-- Engagement
Photo_Votes
  user_id   FK -> Users
  photo_id  FK -> Machine_Photos
  UNIQUE(user_id, photo_id)  -- prevent duplicate votes
  created_at timestamp

Reports
  id          uuid PK
  user_id     FK -> Users
  target_type enum (photo | gym_machine)
  target_id   uuid
  reason      text
  status      enum (pending | reviewed | dismissed | actioned) DEFAULT 'pending'
  reviewed_at timestamp (nullable)
  created_at  timestamp
  -- Auto-blind at 5 cumulative reports (pending status) + admin review
```

### Design Notes

- `Gyms.location` uses PostGIS `geography` type -> `ST_DWithin` for radius search
- `Gyms` has optional operating info (phone, hours, price) — populated gradually via crowdsourcing
- `Gym_Machines.quantity` — a gym can have 2+ of the same machine
- `upvote_count` denormalized -> avoids JOIN/COUNT for sorting
- `Machine_Photos.user_id` is nullable for Phase 1 seed data, enforced at app level in Phase 2+
- `Reports.status` tracks moderation progress (pending -> reviewed -> actioned/dismissed)
- `Machine_Templates` normalizes data -> prevents duplicate entries from different user inputs
- `is_custom` + `is_approved` combo manages crowdsourced data quality
- Fuzzy Matching handled at query time (no dedicated table needed)
- OCR results not persisted (input assistance only, not stored)
- Initial template data via SQL seed file (tracked in Git)

### Upvote Transaction Flow

```
User taps upvote on photo
  -> Supabase (Phase 1) or Spring Boot API (Phase 2+)
  -> BEGIN TRANSACTION
      INSERT INTO photo_votes (user_id, photo_id)
      UPDATE machine_photos SET upvote_count = upvote_count + 1 WHERE id = photo_id
  -> COMMIT
  -> On UNIQUE violation (already voted) -> return error, no count change
```

Phase 1: Supabase RPC function wraps both operations in a single transaction.
Phase 2+: Spring Boot @Transactional on VoteService.upvote().

### Pagination Strategy

All list endpoints use cursor-based pagination:

```
Gym list:      ORDER BY distance ASC, LIMIT 20, cursor = last gym distance
Photo list:    ORDER BY upvote_count DESC, LIMIT 20, cursor = last upvote_count + id
Machine list:  No pagination needed (bounded by gym, typically < 50)
```

- TanStack Query `useInfiniteQuery` on frontend for infinite scroll
- Supabase: `.range(from, to)` for offset-based (Phase 1)
- Spring Boot: cursor-based pagination for better performance (Phase 2+)

### Token Refresh Flow

```
Supabase Auth JWT lifecycle:
  -> JWT issued on login (default expiry: 1 hour)
  -> Refresh token stored in react-native-mmkv
  -> supabase-js client auto-refreshes before expiry
  -> If refresh fails -> redirect to login screen

Phase 2+ (Spring Boot):
  -> App sends JWT in Authorization header
  -> Spring Boot validates JWT (checks expiry, signature)
  -> If expired -> return 401 -> app refreshes via Supabase -> retry request
  -> ky HTTP client: interceptor auto-retries on 401 after token refresh
```

### Database Migration Strategy

```
Phase 1: Supabase SQL Editor (manual execution)
  -> Migration files tracked in: supabase/migrations/

Phase 2+: Two tracks
  -> Supabase schema changes: numbered SQL files (001_initial.sql, 002_add_gym_fields.sql)
  -> Applied via Supabase CLI: supabase db push
  -> Spring Boot: no ORM migration (Supabase owns the schema)
  -> Schema changes always go through Supabase migration files

Versioning: each migration file is idempotent (IF NOT EXISTS, etc.)
```

## 8. Phase 2: Spring Boot + Upload + OCR

**Goal:** Introduce Spring Boot API server, user auth, photo upload -> OCR -> machine data registration.

### Architecture Change

```
Phase 1: Expo -> Supabase direct
Phase 2: Expo -> Spring Boot API -> Supabase

Spring Boot Layer Structure:
+-- Controller (@RestController, @Valid input validation)
+-- Service (@Service, business logic)
+-- Repository (Supabase client / JdbcTemplate for PostGIS)
+-- Config (SecurityConfig, CorsConfig, etc.)
+-- Package structure: com.ironspot.{auth, gym, machine, photo, search}
```

### Auth Flow (Supabase Auth + Spring Security)

```
User -> Social login (Google/Kakao/Apple) in app -> Supabase Auth issues JWT
    -> App sends JWT in Authorization header
    -> Spring Security JwtAuthenticationFilter validates token
    -> SecurityContext populated with user info
    -> Controller processes request
```

- Supabase handles OAuth flow entirely (login, token refresh)
- Spring Boot only validates the JWT signature + extracts user claims
- No OAuth implementation in Spring Boot
- **Apple Sign In is required for iOS App Store submission** (App Store Review Guideline 4.8): if the app offers any third-party social login (Google, Kakao, Facebook, etc.), Apple Sign In must be offered with equivalent prominence. Currently unimplemented — see Phase 2 Pre-Launch Backlog.

### Photo Upload Pipeline (Spring Boot)

```
Client: image resize/compress
    -> POST /api/photos/upload
    -> JwtAuthenticationFilter (JWT verification)
    -> PhotoController -> PhotoService.upload()
        +-- Save image to Supabase Storage (via Supabase Java client)
        +-- Call Google Vision API (OCR)
        +-- Fuzzy match OCR result to Machine_Templates
        +-- Create/update Gym_Machines record
        +-- Create Machine_Photos record
    -> Response: { machine info, OCR recommendation }
```

### Image Storage (Supabase Storage)

```
supabase-storage/
└── machine-photos/
    └── {gym_id}/
        └── {uuid}.webp
```

| Setting        | Value                     |
| -------------- | ------------------------- |
| Max file size  | 2MB (after client resize) |
| Max resolution | 1200x1200                 |
| Format         | webp (best compression)   |
| Free tier      | 1GB (~2,000-3,000 photos) |

- Client compresses before upload (react-native-image-resizer)
- Files named by uuid (no collision)
- Organized by gym_id for management
- Public URL stored in Machine_Photos.photo_url

### New Gym Registration Flow

```
User tries to upload photo -> selects gym -> gym not in our DB
  -> User searches via Naver Maps Places API
  -> Selects a place from Naver results
  -> App extracts: name, address, lat/lng from Naver API response
  -> POST /api/gyms (auto-creates Gyms record with is_verified: false)
  -> User continues with photo upload flow as normal
```

- New gyms start as `is_verified: false` until admin reviews or enough user activity
- Naver Places API provides authoritative name/address/coordinates — no manual coordinate entry
- Prevents duplicate gyms: search our DB first, then Naver only if not found

### Key Technical Points

- Spring Boot layered architecture (Controller/Service/Repository)
- Spring Security filter chain for JWT validation
- Google Vision API integration (monthly 900 call limit + fallback)
- Fuzzy Matching (Levenshtein distance or similar)

## 9. Phase 3: Natural Language Search

**Goal:** Natural language text-to-query pipeline + search UI.

### Pipeline

```
User input: "Find gyms within 1km with at least 5 Panatta machines"
    |
Spring Boot SearchController
    |
SearchService.parseNaturalQuery()
    +-- LLM API call (Claude/GPT)
    +-- Prompt: user input -> structured JSON
    +-- Response example:
    |   {
    |     "location": { "type": "current", "radius_km": 1 },
    |     "filters": {
    |       "brand": "panatta",
    |       "min_count": 5
    |     }
    |   }
    +-- Validate response with Jackson + custom validator
    |
SearchService.executeQuery()
    +-- Structured JSON -> PostGIS SQL
    +-- ST_DWithin(location, user_point, 1000)
    +-- HAVING COUNT(machines) >= 5
    +-- WHERE brand.name ILIKE '%panatta%'
    |
Return results -> Display markers on map
```

### LLM Prompt Design

- System prompt provides: available filters (brand, category, loading_type, radius, min_count)
- Brand/category enum values included as context
- Response must conform to specified JSON schema
- Unparseable input returns `{ "error": "reason" }`

### Key Technical Points

- LLM structured output + Jackson deserialization + validation -> reliable AI pipeline
- Prompt engineering with DB schema as context
- Dynamic SQL generation -> PostGIS query builder
- Filters and NL search share the same query layer -> architectural consistency

## 12. Error Handling Strategy

### App (React Native)

```
[Network Errors]
+-- TanStack Query retry (2 attempts with exponential backoff)
+-- Offline detection -> show cached data + "오프라인" banner
+-- Request timeout: 10s default, 30s for photo upload

[User-Facing Errors]
+-- Toast (burnt) for transient errors ("네트워크 오류, 다시 시도해주세요")
+-- Full-screen error state for critical failures (map load fail, auth fail)
+-- Never show raw error messages to user

[OCR/AI Errors]
+-- OCR timeout or failure -> fallback to manual input (already designed)
+-- LLM parse failure -> return { error: "reason" } -> show "검색 조건을 다시 입력해주세요"
```

### Spring Boot (Phase 2+)

```
[Global Exception Handler] (@RestControllerAdvice)
+-- BusinessException -> 4xx with structured error response
+-- External API failures (OCR, LLM) -> retry once, then fallback
+-- Unexpected errors -> 500 + log full stack trace (never expose to client)

[Structured Error Response]
{
  "success": false,
  "error": {
    "code": "PHOTO_UPLOAD_FAILED",
    "message": "사진 업로드에 실패했습니다"
  }
}
```
